# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> Рабочий язык проекта — русский. Остальной файл написан по-русски, в тон
> `PROJECT_INSTRUCTIONS.md` и `work/`.

## Что это за репозиторий

Это **не обычная кодовая база, а проект развития теории ФТС** («лестница
различимости») поверх неизменяемой канонической выгрузки v13. Python-скрипты —
инструменты доступа и машинной проверки, а не продукт. «Продукт» — это статья,
карточки и решения теории в `work/` (прежде всего пересборка в `work/v14_rebuild/`).

Главный архитектурный принцип: **диск — источник истины, контекст LLM — расходник.**
Сессия может оборваться по лимиту токенов в любой момент, и потеря не должна стоить
больше одного маленького инкремента. Из этого вытекает весь рабочий процесс
(write-through на диск, STATE-handoff, частые коммиты, точечный доступ к канону).

## Первым делом в каждой сессии (обязательно)

Перед любой работой прочитать, в этом порядке:
1. **`PROJECT_INSTRUCTIONS.md`** — контракт сессии и жёсткие гардрейлы (целиком).
2. **`work/STATE.md`** — «где мы»: снимок канона, текущая цель, следующий шаг,
   лог сессий. Свежая сессия поднимается отсюда за один шаг.
3. **`work/notation.md`** — смысл перегруженных символов ФТС (`¬A`/`0_A`/`−A`,
   `⊖`/`Rot`, регистры М/Ч/А, каналы Q/ratio, оверлеи).

CLAUDE.md эти файлы не дублирует — он на них указывает и фиксирует то, что между
ними не записано.

## Команды

Запускать из корня репозитория. На Windows-консоли скрипты печатают кириллицу и
пишут отчёты в UTF-8 — добавляй **`-X utf8`** (иначе возможен `UnicodeEncodeError`).

```
python tools/verify.py                          # целостность канона по SHA256 (ОБЯЗАН быть 0 mismatch)
python tools/query.py stats                     # обзор карточек по типам и статусам
python tools/query.py card U_07                 # карточка + входящие/исходящие рёбра
python tools/query.py context U_07 1            # карточка + соседи, готово вставить в сессию
python tools/query.py find фаза                 # поиск по тексту/заголовку/символу
python tools/query.py deps OP_Lift              # транзитивное depends_on
python -X utf8 tools/oq_pool.py --write         # пулы пересекающихся открытых вопросов → work/OQ_POOLS.md
                                                # (курируемый слой поверх — work/OQ_TRIAGE.md)

python -X utf8 work/v14_rebuild/verification.py        # «тесты» теории: машинная проверка C01..C59
python -X utf8 work/v14_rebuild/crosscheck.py grounds  # сверка ссылок статьи с каноном (секции: grounds|levels|sp|fails|find <q>|keys)
python -X utf8 work/v14_rebuild/o20/run_o20.py         # внешний эмпирический тест (по пред-регистрации)

python tools/import_from.py "C:\путь\к\выгрузке"        # доустановка/обновление канона из папки + verify
```

`verification.py` — это **тест-сьют теории**: каждое формальное утверждение статьи
привязано к проверке `C-NN`, скрипт пишет `verification_report.md` и возвращает
код 0 только если все PASS (сейчас **59 PASS / 0 FAIL**, C01–C59). FAIL любой
проверки автоматически лишает соответствующее утверждение права на статус
`formal_math_fact` — это не «упавший тест на потом», а отзыв статуса.

Запускать одиночную проверку отдельно нельзя — скрипт прогоняет все `check(...)`
за раз; смотри нужный `C-NN` в выводе или в `verification_report.md`.

Зависимости: Python 3.13, `sympy` (verification), `numpy`/`pandas`/`scipy`/
`scikit-learn` (эксперимент o20). Файла requirements нет — окружение пользователя.

## Архитектура и поток данных

- **`source/`** — **канон v13, неизменяемый** (`v13_complex_branch_overlay`:
  161 карточка, 238 триплетов, 54 листа). Это выгрузка из xlsx; целостность задана
  `MANIFEST.json` + SHA256. **Руками не редактировать.** Новая версия теории =
  новая выгрузка + новый MANIFEST, а не правка файлов. Корпус велик (дамп 442 КБ,
  workbook 912 КБ) — целиком в контекст не грузить, только через `tools/query.py`.
  Модель карточки (`fts_cards.jsonl`): `id, type, status, title, symbol, text,
  depends_on, tags, ...`; граф — в `fts_triples.tsv` (`subject  predicate  object`).

- **`tools/`** — `verify.py` (SHA256-сверка), `query.py` (точечный graph-retrieval
  без БД, читает `fts_cards.jsonl` + `fts_triples.tsv`), `import_from.py` (перенос
  выгрузки в `source/` + сверка). ROOT вычисляется от `__file__`, так что запуск
  работает из любого cwd.

- **`work/`** — **вся разработка**. `STATE.md` (handoff между сессиями),
  `DECISIONS.md` (журнал значимых решений: что и почему), `OPEN_QUESTIONS.md`
  (очередь инкрементов), `notation.md` (словарь символов).

- **`work/v14_rebuild/`** — **активный проект**: `FTS_v14_paper.md` (научная
  статья — основной артефакт), `verification.py` + `verification_report.md`
  (машинная проверка), `status_patch_v14.md` (повышения статусов через SP-карточки),
  `FTS_v14_register_map.md` (карта регистров/каналов/оверлеев), `red_team_F3.md`
  (атаки красной команды), `crosscheck.py`/`sheet_dump.py` (точечный доступ),
  `o20/` (первый внешний эмпирический тест: `PREREGISTRATION.md` коммитится ДО
  прогона, затем `run_o20.py` → `results.json`/`RESULTS.md`).

Связи между артефактами: утверждение в `paper.md` → проверка `C-NN` в
`verification.py` → ссылка на `[карточка ID]`/`[лист row]` в `source/`, сверенная
через `crosscheck.py`. Разрывать эту цепочку нельзя (см. no-smuggling ниже).

## Инварианты, которые нельзя нарушать

1. **Канон неизменяем и проверяем.** Перед серьёзной работой `tools/verify.py`
   обязан давать `0 missing, 0 mismatch`. Все правки — только в `work/`.

2. **Нормализация переводов строк в git ОТКЛЮЧЕНА** (`core.autocrlf=false` +
   `.gitattributes`: `source/** -text`, `*.tsv -text`, `*.jsonl -text`). SHA256
   требует байтовой идентичности; git-нормализация молча ломала канон при checkout.
   **Не включай autocrlf и не снимай `-text` с `source/`** — иначе verify покажет
   mismatch на ровном месте.

3. **No-smuggling (главный риск теории).** У понятий ФТС нет априорного смысла в
   обучающих данных — нельзя молча подставить стандартный матсмысл перегруженного
   термина. Любой нетривиальный вывод помечать источником: `[карточка ID]`,
   `[триплет s→p→o]`, `[лист row]` либо `[внешнее]`. При конфликте внешнего знания
   с каноном **побеждает канон**. Чего нет в артефактах — писать дословно
   `нет в артефактах`, не выдумывать.

4. **Не смешивать сущности:** `¬A` ≠ `0_A` ≠ `−A`; `candidate`/`overlay` ≠
   `canonical_strict`; `phase ≠ −A`; `branch access ≠ Lift`; `array ≠ tensor`
   (пока не задан закон преобразования); М-регистр ≠ Ч-регистр ≠ оверлей.
   Полный список — в `PROJECT_INSTRUCTIONS.md` §3 и `work/notation.md`.

5. **Статусная дисциплина.** Повышение статуса — только через карточки `SP_*` и
   явные критерии канонизации К1–К5 (формальный свидетель + основания + гардрейлы
   + ретродикция + условие поражения), с подтверждением в графе. Запрет `SP_LIMITS`
   (верхние уровни — предсказания, не канон) соблюдать. Порядок статусов — в
   `notation.md`.

6. **Формат вывода для анализа:** `Найдено → зависимости → вывод → что не закрыто.`

## Конец сессии (ритуал, при приближении лимита токенов)

1. Обновить `work/STATE.md`: что сделано, что в работе, следующий шаг, открытые
   нити — указателями, не пересказом.
2. Значимое решение — строкой в `work/DECISIONS.md` (что и почему).
3. Закрытый пункт — отметить в `work/OPEN_QUESTIONS.md` со ссылкой на карточку/коммит.
4. `git add -A && git commit` — каждый осмысленный шаг отдельным коммитом
   (откат и diff всегда доступны). Дробить работу на единицы «одна лемма / одна
   карточка за раз»; писать на диск сразу (write-through), а не копить к концу.
