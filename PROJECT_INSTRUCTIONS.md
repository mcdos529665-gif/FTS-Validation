# PROJECT_INSTRUCTIONS — ФТС v13, рабочий проект

Этот файл — первое, что читает LLM в начале каждой сессии. Он задаёт правила
работы с теорией ФТС, которой нет в обучающих данных модели.

## 0. Источник истины

- `source/` — **активный канонический релиз**. Исторический v13 — это выгрузка из
  `ФТС_табличный_канон_v13_complex_branch_overlay.xlsx` (161 карточка, 238 триплетов,
  54 листа). Целостность проверяется `python tools/verify.py` по SHA256 из MANIFEST.
  По умолчанию канон не редактируется. Но прямая команда автора «исправь»,
  «исправь/замени канон», «замени формулу в каноне» или равнозначная формулировка
  означает: **сразу выполнить замену активного канона**, а не создать только
  supplement или предложение. Перед заменой предыдущий релиз сохраняется в
  `work/canon_history/<release-id>/`; затем обновляются активные файлы,
  `MANIFEST.json` и все производные представления.
- `work/` — **здесь идёт разработка**: STATE, решения, открытые вопросы, нотация,
  черновики новых карточек/лемм. Всё новое попадает сюда.
- `tools/` — утилиты (`verify.py`, `query.py`, `import_from.py`).

Авторское решение 2026-09-19 добавило версионированное дополнение к канону:
[`work/AUTHOR_CANON.md`](work/AUTHOR_CANON.md). Читать его при работе с У0,
логическими формами У6/У7 и ожиданием модели. Прямо принятые автором положения
этого пакета действуют в своей области. До прямой команды на замену `source/`
и `tools/query.py` сохраняют исторический снимок v13; после такой команды они
должны показывать новый активный релиз. Авторское принятие не означает математического
доказательства, эмпирической проверки или автоматического повышения старых
SP-карточек. Полный объединённый workbook пока не переиздан.

### 0.1. Работа с источниками arXiv

Для каждой добавляемой статьи с [arXiv](https://arxiv.org/) заводить отдельный
каталог статьи. Внутри него обязательно хранить:

- `source/` — оригинальные исходники статьи;
- `original.pdf` — официальный PDF;
- `article.md` — производную Markdown-версию.

`<каталог статьи>/source/` — неизменяемый первичный источник: не редактировать,
не переформатировать и не восстанавливать по Markdown. Корневой `source/`
остаётся активным каноническим релизом ФТС; исторические релизы живут в
`work/canon_history/`, а исходники arXiv всегда живут только во
вложенном `source/` соответствующего каталога статьи.

При расхождении Markdown и LaTeX приоритет имеет LaTeX; `original.pdf`
используется для проверки визуальной структуры; `article.md` исправляется по
исходнику, а не наоборот.

## 1. Контракт сессии (обязателен)

**Старт каждой сессии:**
1. Прочитать `PROJECT_INSTRUCTIONS.md` (этот файл) и `work/STATE.md`.
2. Прочитать `work/notation.md` — там смысл перегруженных символов ФТС.
3. Под текущую задачу подтянуть ТОЛЬКО релевантные карточки/рёбра через
   `tools/query.py` (см. §4). Не загружать весь корпус.

Стартовые файлы читать один раз за сессию; повторять чтение при изменении
нужного файла или потере контекста. Подробные документы выбирать по задаче:
[карта документов](work/DOCUMENT_MAP.md). Новое обозначение и краткий смысл —
в `notation.md`; полный разбор — в существующий тематический пакет; точная
реплика автора — в журнал; текущий шаг и ссылка — в `STATE.md`. Если разбор
уже есть, ссылаться на его раздел вместо добавления пересказа в стартовые файлы.

**Выход / при приближении лимита токенов:**
1. Записать в `work/STATE.md` краткий handoff: что сделано, что в работе,
   следующий шаг, открытые нити. Не пересказ — указатели.
2. Значимое решение — строкой в `work/DECISIONS.md` (что и почему).
3. Закоммитить (`git add -A && git commit`). Контекст одноразовый — диск есть истина.

Дробить работу на единицы, влезающие в одну сессию: «одна лемма / одна карточка за раз».
Писать на диск сразу (write-through), а не копить к концу.

## 2. Правило «не подмешивать» (no-smuggling)

Для понятий ФТС у модели нет априорных знаний. Главный риск — молча подставить
стандартный математический смысл перегруженного термина и связно противоречить канону.

- Любой нетривиальный вывод помечать источником: **[карточка ID]**, **[триплет s→p→o]**,
  **[лист row]**, либо **[внешнее]** — если опираешься на общематематическое знание.
- При конфликте внешнего знания с каноном ФТС — **побеждает канон**, внешнее только
  сигнализируется, не применяется молча.
- Если сущности нет в артефактах — писать дословно `нет в артефактах`, не выдумывать.
- Если ты ловишь себя на том, что мысленно «переформулируешь» правило ФТС в привычное —
  это сигнал остановиться и свериться с карточкой, а не продолжать.

## 3. Правила чтения регистров и формат анализа

- М-регистр — минимальная проекция выражения; Ч-регистр — операциональное чтение
  (Dist₃, Select, Agg, K и т.д.). Не путать регистры.
- Формат вывода для анализа: **Найдено → зависимости → вывод → что не закрыто.**

## 4. Как не загружать весь корпус

Корпус слишком велик для одного контекста (полный дамп 442 КБ, workbook 912 КБ).
Работать точечно через `tools/query.py` (БД не нужна):

    python tools/query.py stats                # обзор: типы и статусы
    python tools/query.py card U_07            # карточка + входящие/исходящие рёбра
    python tools/query.py context U_07 1        # карточка + соседи (готово вставить в сессию)
    python tools/query.py neighbors U_07 2      # подграф на 2 шага
    python tools/query.py deps OP_Lift          # транзитивные depends_on
    python tools/query.py find фаза             # поиск по тексту/заголовку/символу
    python tools/query.py status candidate      # всё со статусом-кандидатом
    python -X utf8 tools/claim_graph.py build  # авторитетный directed claim/evidence graph
    python -X utf8 tools/claim_graph.py validate --idempotent
    python -X utf8 tools/claim_graph.py search "не-предмет У0"
    python -X utf8 tools/claim_graph.py query CM-001 --depth 1
    python -X utf8 tools/claim_graph.py path CM-001 C01

Полные `FULL_DUMP.md` / `workbook_sheets.json` открывать только когда нужен
лист целиком — и тогда конкретный лист, а не файл целиком.

`work/v14_rebuild/claim_graph/claim_graph.json` — авторитетный машинный слой
утверждений, источников, evidence, ограничений и статусных оценок. Он сохраняет
направление и параллельные предикаты независимо от `graphify-out/`; Graphify
используется как навигационное представление. `CLAIM_MATRIX.tsv` представлена
групповыми claims, атомаризация без свидетеля запрещена. C01–C62 являются
evidence формальных предикатов и сами по себе не повышают `St_FTS`. Все curated
bridges обязаны иметь scope, provenance и `status_effect`.

## 5. Восстановление при истечении токенов

- Диск — источник истины, контекст — расходник. Потеря сессии не должна стоить больше
  одного маленького инкремента.
- `work/STATE.md` всегда отражает «где мы». Свежая сессия поднимается из него за 1 шаг.
- Каждый осмысленный шаг — git-коммит (откат и diff всегда доступны).
- Канон проверяем: `python tools/verify.py` обязан давать 0 mismatch перед серьёзной работой.
